# 이메일 초대와 회원가입 없는 채팅방 참여

2026-10-22에 추가된 제품 요구사항입니다. 기존 architecture.md의 기술 스택을 유지하면서, 계정·참여자·인증 설계는 이 요구사항에 맞춰 확장합니다. 회원·게스트 참여자 모델과 회원 인증·방 생성 코드는 작성되어 있으며, DB에는 새 마이그레이션을 적용해야 합니다. 초대 발송·수락과 게스트 세션은 아직 구현 전입니다.

## 확정된 요구사항

- 회원가입 기능은 제공하지만, 초대받은 사람이 채팅에 참여하기 위한 필수 조건은 아닙니다.
- 채팅방 생성과 이메일 초대 발송은 회원가입·로그인을 완료한 회원만 할 수 있습니다. 초대 발송에는 해당 방의 초대 권한도 필요합니다.
- 앱의 핵심 진입 경로는 초대 메시지입니다. 첫 전달 수단은 이메일입니다.
- 초대를 수락하면 해당 채팅방에서 사용할 참여자 신원이 생깁니다.
- 가입하지 않은 참여자는 초대를 수락한 방에서만 대화할 수 있습니다. 다른 방이나 회원 계정의 권한을 얻지 않습니다.

## 참여 흐름 제안

1. 회원이 가입·로그인하여 채팅방을 만들고, 해당 방에서 수신자의 이메일 주소를 입력합니다. 기존 방에서도 로그인한 회원 중 초대 권한이 있는 사람만 초대를 보낼 수 있습니다.
2. 서버가 해당 방에 연결된 초대를 만들고 참여 링크를 이메일로 보냅니다.
3. 수신자가 링크를 열어 초대 내용을 확인합니다.
4. 수신자가 표시 이름을 입력하고 참여를 수락합니다. 회원가입이나 비밀번호 입력은 요구하지 않습니다.
5. 서버가 초대를 검증하고 방 전용 참여자와 세션을 생성합니다.
6. 참여자는 바로 해당 방의 대화 화면으로 이동합니다.

표시 이름 입력과 수락 화면은 제안입니다. 링크를 여는 GET 요청만으로 초대를 소모하거나 참여자를 생성하지 않습니다. 실제 수락은 명시적인 POST 요청으로 처리해 이메일 링크 미리보기가 초대를 먼저 사용하지 않도록 합니다.

## 계정과 참여자의 구분

회원 계정은 서비스에서 로그인하는 신원이고, 방 참여자는 특정 방에서 대화하는 신원입니다. 두 개념을 분리하면 비회원도 메시지 작성자, 읽음 위치, 참여 상태를 가질 수 있습니다.

| 개념 | 설계 방향 |
| --- | --- |
| 회원 계정 | 기존 users의 가입·로그인 책임을 유지합니다. |
| 방 참여자 | room_members에 독립 ID, MEMBER/GUEST 구분, 표시 이름, 선택적인 회원 계정 연결, 퇴장 시점을 둡니다. 비회원은 해당 방 안에서만 식별합니다. |
| 초대 | 방, 수신 이메일, 발신 회원, 토큰 해시, 만료·수락·취소 상태를 관리합니다. |
| 게스트 세션 | 참여자와 방을 지정하여 해당 범위의 접근만 허용합니다. |
| 메시지 | 회원과 게스트 모두 작성할 수 있도록 방 참여자를 작성자로 연결합니다. |

같은 이메일 주소라는 이유만으로 기존 회원 계정에 로그인시키거나, 다른 방의 게스트 신원을 합치지 않습니다. 여러 방에서 각각 초대를 수락한 경우에도 각 참여 권한을 독립적으로 확인합니다.

## 접근 권한과 초대 수락

- 방 생성과 이메일 초대 발송 요청은 서버에서 회원 로그인 여부를 확인합니다. 초대 발송은 해당 방의 초대 권한도 확인하며, 회원이라는 이유만으로 다른 방에서 초대할 수는 없습니다.
- 게스트 세션으로 허용하는 대상은 초대를 수락한 방의 대화 기능입니다. 게스트의 방 생성, 타인 초대, 회원 관리 요청은 거부합니다.
- REST의 내역 조회와 메시지 요청, Socket.IO의 방 구독과 전송 모두 서버에서 세션 범위와 현재 참여 권한을 확인합니다. 요청에 들어온 roomId나 화면에서 숨긴 메뉴만으로 권한을 판단하지 않습니다.
- 초대 링크는 추측하기 어려운 토큰을 사용하고 DB에는 토큰 원문 대신 해시를 저장하도록 설계합니다. 토큰에는 유효기간을 두고 수락 후 재사용하지 않습니다.
- 초대 수락과 참여자·세션 생성은 하나의 트랜잭션에서 처리하여 동시 수락으로 중복 참여자가 생기지 않게 합니다. 같은 브라우저의 성공한 수락 재시도는 기존 세션으로 처리하는 방식 등을 구현 시 정합니다.
- 초대 토큰과 참여 세션은 구분합니다. 수락 후에는 세션으로 재접속하며, 세션 만료 시 복귀 방식은 별도로 결정합니다.
- 초대가 취소되었거나 만료된 경우 새 참여를 허용하지 않습니다. 이미 참여한 사람의 접근 차단은 참여 권한과 활성 세션·소켓에도 반영해야 합니다.
- 이메일 링크는 소지자가 사용할 수 있는 자격 증명입니다. 링크를 전달받은 제삼자까지 차단해야 하는지는 별도 정책으로 결정합니다. 링크만으로 특정 사람의 이메일 소유권을 강하게 보장한다고 표현하지 않습니다.

## 현재 코드에서 필요한 변경

현재 구현에는 초대 발송, 초대 수락, 게스트 인증 기능이 없습니다. 아래는 이미 작성한 기반과 후속 변경 사항입니다.

- Prisma (작성됨): room_members는 독립 ID를 가지며 user_id가 선택 사항입니다. kind와 계정 연결의 일치 여부, 게스트의 OWNER 역할 금지, 메시지 작성자가 같은 방의 참여자인지를 DB 제약으로 보장합니다. 기존 메시지의 작성자 연결을 보존하는 새 마이그레이션을 추가했습니다.
- Prisma (후속): 초대와 게스트 세션 저장 구조를 추가합니다. 현재 member_sessions는 회원 전용입니다. 이미 적용한 마이그레이션을 수정하지 않고 새 마이그레이션으로 변경합니다.
- 방 생성 계약 (작성됨): 방 이름만 입력받고 로그인한 회원을 유일한 초기 참여자로 등록합니다. 현재 새 방은 GROUP으로 생성합니다. 기존 DIRECT 방과 directKey는 보존하며, 초대 기반 1:1 방 정책은 후속 단계에서 정합니다.
- API: invitations 모듈, 이메일 발송 어댑터, 초대 수락 처리와 게스트 세션 검증을 추가합니다. 회원 인증과 게스트 세션의 권한 범위를 구분합니다.
- 공유 계약: 회원 계정과 방 참여자의 응답 타입을 구분하고 초대 요청·조회·수락 형식을 정의합니다. 수신 이메일과 토큰 해시를 일반 참여자 응답에 노출하지 않습니다.
- 웹: 이메일 초대 입력, 초대 확인·참여 화면, 해당 방으로의 이동과 게스트 세션 복귀를 구현합니다. 이메일 링크에서 웹으로 참여할 수 있게 합니다.
- 모바일: 같은 초대 계약을 사용합니다. 앱으로 직접 여는 링크 연결은 모바일 참여 흐름 구현 시 함께 다룹니다.

## 아직 결정하지 않은 정책

- 초대 링크와 게스트 세션의 유효기간, 브라우저 변경·쿠키 삭제 후 재입장 방법.
- 참여 이전 메시지를 게스트에게 어디까지 공개할지.
- 링크 전달 허용 여부와 추가 수신자 확인 필요 여부.
- 실제 이메일 발송 서비스와 발신 주소. 서비스 연결 전에는 실제 발송 완료로 표시하지 않습니다.

## 구현 확인 기준

- 로그인한 회원은 방을 만들고, 초대 권한이 있는 방에서 이메일 초대를 보낼 수 있습니다.
- 미인증 요청과 게스트 세션으로는 방 생성·초대 발송을 할 수 없습니다. 회원도 초대 권한이 없는 방에서는 초대 발송이 거부됩니다.
- 회원가입 없이 유효한 이메일 초대를 수락하고 해당 방에서 대화할 수 있습니다.
- 다른 방의 ID로 REST 요청이나 소켓 이벤트를 보내도 읽기·쓰기·구독이 거부됩니다.
- 만료·취소·이미 사용된 초대로 새로운 참여 세션을 만들 수 없습니다.
- 동시 수락 요청이나 네트워크 재시도로 참여자가 중복 생성되지 않습니다.
- 같은 이메일의 회원 계정이 있어도 초대 수락만으로 그 계정의 다른 방에 접근할 수 없습니다.
- 권한이 회수되면 기존 소켓을 통한 수신과 전송도 중단됩니다.
